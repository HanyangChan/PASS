# A안 서브 에이전트 구현 계획

작성일: 2026-11-05
상태: **설계안. 이 문서의 Supervisor·전문 에이전트·종합 판단 에이전트는 아직 구현하지 않는다.**

## 1. 목표와 현재 구현의 경계

현재 구현은 규칙 Router, 미해석 발화에 대한 단일 LLM 조건 추출, 공통 추천 엔진·검증이다. 목표는 미해석 발화의 해석을 `LLM Supervisor → 필요한 전문 에이전트 → 종합 판단`으로 확장하는 것이다.

각 서브 에이전트는 역할별 프롬프트·입출력 계약·검증·테스트를 가진 논리 모듈로 만든다. 초기에는 동일한 서버와 `deepseek-v4-flash`를 사용한다. 별도 서버나 프로세스를 띄우지 않는다. 통신은 공통 `baseline/llm/`를 재사용한다.

규칙으로 확정할 수 있는 요청은 지금처럼 LLM 호출 0회를 유지한다. 모든 발화를 무조건 여섯 번의 모델 호출로 처리하지 않는다. 추천 상품·순위·가격·배송비 계산은 계속 기존 PASS 엔진만 수행한다.

## 2. 전체 처리 순서

1. 기존 Router가 입력·세션을 검증하고 추천·조건 수정·설명·예산 비교 의도를 분류한다.
2. 규칙으로 처리 가능한 요청, 충돌 예산 확인, 기존 엔진 기반 설명·가상 비교는 기존 경로에서 끝낸다.
3. 미해석 발화만 서브 에이전트 해석기에 전달한다. 현재 입력·확정 조건·미해결 질문과 필요한 최근 대화만 사용한다.
4. LLM Supervisor가 필요한 전문 에이전트와 각자의 분석 과제를 구조화해 반환한다.
5. 서버 코드가 선택 목록과 호출 예산을 검사한 뒤 선택된 전문 에이전트들을 병렬 실행한다.
6. 서버 코드가 각 결과의 형식·담당 필드·근거를 먼저 검증한다.
7. 종합 판단 에이전트가 유효한 분석 결과를 합쳐 최종 조건 후보 또는 확인 질문을 만든다.
8. 서버가 최종 후보를 다시 검증한다. 확정 가능한 경우에만 기존 상태 적용 경로로 보내고 추천 엔진을 실행한다.
9. 모호하거나 충돌하면 조건을 바꾸지 않고 질문한다. 공급자 실패는 기존 재시도 가능한 오류 경로로 반환한다.

외부 Router는 실행·종료와 호출 한도를 통제한다. LLM Supervisor는 정해진 전문 역할 중 무엇이 필요한지 제안하며, 임의 도구 실행이나 재귀적 에이전트 호출 권한은 갖지 않는다.

## 3. 에이전트별 책임

| 모듈 | 입력과 책임 | 출력 | 하지 않는 일 |
| --- | --- | --- | --- |
| LLM Supervisor | 미해석 발화·확정 상태·미해결 질문을 보고 분석할 역할과 과제를 선택 | 허용된 역할 ID 목록, 역할별 과제·근거 참조 | 상품 선택, 조건 적용, 임의 역할 생성, 재계획 루프 |
| 수령인 분석 | 선물 수령인, 관계 표현, 주는 사람/받는 사람/불명인 조건 귀속, 대상 변경 분석 | 수령인 후보, 귀속 정보, 모호한 지점 | 나이·성별·관계만으로 취향 확정, 다른 수령인 기억 적용 |
| 상황·명절 | 명시된 기념일·명절·선물 목적·포장·수령 마감일 해석 | 상황·포장·날짜 후보와 확인 질문 | 달력 근거 없이 명절 날짜나 배송 가능일 생성 |
| 소비 성향 | 주는 사람의 명시적 예산·배송비 포함 여부·브랜드 조건 해석, 가격 관련 추상 표현 식별 | 예산 등 명시 조건, 확정할 수 없는 가격 표현 | 구매력·소득·성격 추정, 예산 자동 증액, 비싼 상품 우대 |
| 취향 추론 | 받는 사람의 명시적 선호·부정·제외·성분 회피 해석, 간접 표현의 불확실성 표시 | 선호·제외 후보, 근거, 확인할 추론 | 알레르기 진단, 상품 안전 보장, 불명인 취향 자동 확정 |
| 종합 판단 | 검증된 전문 결과와 확정 상태의 차이를 통합하고 충돌·귀속 불명을 정리 | `{patch, questions, unresolved}` | 원문 근거 없는 사실 추가, 하드 제약 완화, 추천 순위 계산 |

취향 **추론**의 결과는 명시 사실과 구분한다. 예를 들어 “차분한 분”에서 “차를 좋아한다”로 바꾸지 않는다. 현재 상태 스키마에 없는 추상 요구는 내부 참고 후보로 두거나 질문하며, 엔진에 없는 태그·점수를 새로 넣지 않는다.

초기에는 장기 기억 저장·자동 구매 학습을 추가하지 않는다. 기존 앱의 명시적 개인화 흐름을 유지한다. 수령인 표시 문자열을 장기 기억의 안정적인 ID로 간주하지 않는다.

## 4. 내부 분석 계약

전문 결과는 최종 `patch`와 별개로 아래 정보를 갖는 구조를 계획한다.

| 항목 | 의미 |
| --- | --- |
| `agentId` | 고정된 역할 ID |
| `status` | `complete`, `needs_clarification`, `not_applicable` |
| `observations` | 담당 필드별 분석 후보. 값, 귀속 대상, 명시/추론 구분 포함 |
| `evidenceRefs` | 현재/과거 사용자 발화의 근거 위치 또는 서버가 전달한 확정 상태 필드 참조 |
| `questions` | 확정에 필요한 질문 후보. 한 턴에 사용자에게 표시할 질문은 최대 1개 |

전송·파싱 실패는 위 정상 상태를 흉내 내지 않고 서버 오류로 별도 취급한다. 에이전트 입력은 읽기 전용 상태 복사본이다. 어떤 전문 에이전트도 실제 세션을 직접 수정하지 않는다.

근거 참조는 서버가 제공한 메시지 ID·범위 또는 상태 필드에 연결하고, 인용이 실제 입력에 존재하는지 검사한다. LLM이 작성한 확인 질문을 사용자가 확정한 사실로 재사용하지 않는다. 모델이 출력한 숫자형 자신감만으로 사실을 확정하지 않는다.

필드 소유권은 다음과 같이 시작한다.

- 수령인 분석: `recipients` 후보와 모든 관찰의 귀속 검토.
- 상황·명절: `occasion`, `packaging`, `delivery_by`.
- 소비 성향: `budget`, 명시적 `brand`, 수량/예산 범위의 모호성. 현재 앱은 선물 하나 제약을 유지한다.
- 취향 추론: `preferences`, `excluded_categories`, `excluded_ingredients`.

다른 역할의 필드를 출력하면 서버 검증에서 거부한다. 종합 판단은 소유자가 제공한 유효한 관찰만 최종 필드로 합칠 수 있다. 현재 열거형 밖의 선호·카테고리·성분은 자동 추가하지 않는다.

## 5. 상태 적용과 충돌 해결

우선순위는 **현재 사용자의 명시적 수정 → 같은 수령인의 확정 상태 → 근거가 있는 새 후보 → 불확실한 추론**으로 정한다. 단, 같은 발화 안의 상충 조건은 순서로 덮어쓰지 않고 질문한다.

- “나는 단 걸 좋아하고 엄마는 설탕을 피해”: 주는 사람 선호를 분리하고 엄마의 조건만 후보로 만든다. 설탕 회피를 지원 상태로 어떻게 표현할지 불명확하면 질문한다.
- “10만원 이하인데 최소 15만원”: 상한을 하나 확인한다. 모델 투표로 금액을 정하지 않는다.
- 수령인 변경: 기존 수령인의 선호·제외·예산을 초기화하고 이번 대상의 명시 조건만 적용한다. 수령인을 처음 정하는 경우에는 앞서 입력한 조건을 유지한다.
- 모델의 미언급·생략을 이유로 기존 제외 성분을 삭제하지 않는다. 명시적 해제와 수령인 변경은 기존 코드 정책에 따라 구분한다.
- 명절의 상대 날짜는 서버 기준 일시와 권위 있는 달력 근거가 없으면 확인한다. 초기 구현에 달력 검색 도구는 포함하지 않는다.
- 해결되지 않은 중요한 조건이 있으면 `patch: {}`, `unresolved: true`로 반환한다. 초기 버전은 후보를 일부만 실제 상태에 적용하지 않는다.

서브 에이전트 분석은 요청 시작 시의 동일한 상태 스냅샷에서 수행한다. 최종 적용은 한 번만 한다. 앱의 새 대화·계정 전환·취소 후 이전 분석 결과가 적용되지 않아야 한다.

공통 코어의 상태 버전 검사는 유지한다. 다만 현재 프로토타입 API는 요청별 무상태 어댑터이므로, 이 변경만으로 서버 영속 세션·원자적 CAS·다중 기기 충돌 해결이 생기지는 않는다. 별도 서버 저장 설계 없이 최신 상태를 보장한다고 표시하지 않는다.

## 6. 호출·시간 예산

다음 값은 구현 시작을 위한 **제안값**이며 실측 후 조정한다.

| 단계 | 논리 LLM 호출 상한 | 단계 제한 시간 | 출력 토큰 상한/호출 |
| --- | --- | --- | --- |
| 기존 규칙 경로 | 0 | 기존 실행 경로 | 0 |
| Supervisor | 1 | 최대 4초 | 400 |
| 전문 에이전트 | 선택한 역할당 1회, 최대 4회 | 병렬 단계 전체 최대 8초 | 500 |
| 종합 판단 | 1 | 최대 4초 | 700 |

서브시스템 전체는 현재 해석기의 18초 제한 안에서 끝내며 약 2초를 검증·취소·응답 처리에 남긴다. 전문 역할은 보통 1~2개만 선택하도록 설계하되, 최대 논리 호출은 `1 + 4 + 1 = 6`회다. 전부 선택하면 출력 토큰 설정 상한 합계는 3,100토큰이다. 입력 토큰은 별도로 측정하고, 역할별로 필요한 문맥만 전달한다.

공통 전송기의 5xx 재시도 1회를 유지하면 HTTP 시도는 최대 12회가 될 수 있다. 각 호출의 제한 시간은 해당 단계의 남은 시간 이하로 설정하고 동일한 취소 신호를 전달한다. 재시도가 전체 제한을 늘리게 하지 않는다. 숨은 자기 수정 호출·다른 모델로 자동 전환·무제한 재계획은 초기 범위에 포함하지 않는다.

현재 실제 DeepSeek 단일 사례가 약 5초 걸린 적이 있으므로 위의 4초 Supervisor/종합 판단 제한은 달성된 성능이 아니다. 실제 병렬 실행 지연·실패율을 측정해 짧은 출력으로 가능한지 확인한 후 활성화한다. 현재 앱의 25초 요청 제한도 함께 고려한다.

## 7. 실패 정책과 관측 정보

초기 버전은 선택한 전문 에이전트를 모두 필수로 취급한다. 하나라도 공급자·파싱·근거 검증에 실패하면 부분 분석으로 조건을 적용하지 않고 기존 재시도 가능한 오류 경로를 사용한다. 모델이 정상적으로 “불명확하다”고 판단한 경우는 서비스 장애와 구분해 질문한다.

Supervisor가 역할을 0개 선택하면 바로 질문하거나 기존 규칙 경로로 종료한다. 빈 분석을 채우기 위해 불필요한 종합 호출을 하지 않는다. 한 단계가 실패했을 때 현재 단일 추출기를 추가 호출해 결과를 덮는 자동 폴백은 두지 않는다.

기록할 정보:

- 실행 ID, 선택 역할, 단계 성공/실패·오류 코드, 사용한 입력 상태 버전/스냅샷 식별자.
- 단계별 지연·토큰 사용량, 실제 논리 호출 수와 HTTP 재시도 수.
- 최종 질문 여부, 적용 필드명, 적용/거부 사유 코드.

모델 내부 추론·API 키·원문 대화 전체는 실행 로그에 남기지 않는다. 오류 상태는 확정 분석처럼 보이지 않게 구분한다. 현재 `routing.llmCalls`는 외부 해석기 호출 수를 세므로 다중 호출 도입 시 실제 하위 논리 호출 수와 구별되도록 진단 계약을 수정해야 한다.

## 8. 예정 파일과 연결 지점

아래 파일은 **향후 생성할 목록**이며 이번 계획 작성에서는 만들지 않는다.

```text
baseline/agents/a-router/subagents/
  contracts.mjs       내부 분석·근거·필드 소유권 계약
  prompts.mjs         역할별 프롬프트와 버전
  supervisor.mjs      역할 선택
  recipient.mjs       수령인·귀속 분석
  occasion.mjs        상황·명절 분석
  spending.mjs        명시 예산·가격 표현 분석
  taste.mjs           선호·제외 분석
  synthesizer.mjs     최종 조건 후보 통합
  interpreter.mjs     단계 실행·병렬 호출·호출 예산·취소
```

호출부는 `createSubagentInterpreter({env})`가 기존 `{text, state, pendingQuestion, history, signal} → {patch, questions, unresolved}` 계약의 함수를 반환하는 형태로 계획한다. 공통 엔진 계약은 바꾸지 않는다.

`api/router-agent.mjs`에서 기존 단일 조건 추출 경로 또는 위 해석기를 선택해 `createAgent({interpret})`에 연결한다. 기존 `extract`는 앱 세션 전체를 반환하므로 새 해석기를 그대로 `extract` 자리에 넣지 않고 입출력 계약을 구분한다.

서버 전용 설정 `A_ROUTER_LLM_MODE=single|subagents`를 제안한다. 기본값은 기존 `single`로 유지하고 검증 후 `subagents`를 활성화한다. 공통 main의 `baseline/llm/`, 다른 아키텍처 폴더, `src/vendor/` 추천 엔진에는 A안 전용 로직을 넣지 않는다.

## 9. 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 계약·필드 소유권·근거 참조와 실패 정책 확정 | 예제 입력/출력과 충돌 사례를 고정하고 검증 테스트 작성 |
| 2 | 네 전문 에이전트의 역할별 프롬프트·검증 구현 | 각 역할의 명시/추론/귀속 불명·담당 외 필드 테스트 통과 |
| 3 | Supervisor와 병렬 실행기 구현 | 필요 역할만 실행, 잘못된 ID·중복·호출 초과 차단, 제한 시간·취소 테스트 통과 |
| 4 | 종합 판단·최종 검증 구현 | 미지원 값·근거 없는 추가·하드 제약 삭제 거부, 충돌 시 단일 질문 |
| 5 | 기존 API의 선택 가능한 해석기로 연결 | 규칙 경로 0회 유지, 기존 응답 형식·음성·첨부 UI 회귀 없음 |
| 6 | 단일 추출기와 비교·실제 플랫폼·화면 검증 | 아래 수용 기준 충족 후에만 서브 에이전트 모드 활성화 |

먼저 모의 LLM으로 실패·취소·스키마 경계를 검사하고, 다음에 합성 입력으로 실제 DeepSeek를 시험한다. 실제 계정 화면 검증과 모의 인증 API 검증은 결과를 구분해서 기록한다.

## 10. 수용 기준과 비교 실험

- 명확한 조건·일반 추천·기존 설명·가상 예산 비교는 기존처럼 LLM 0회다.
- 같은 카탈로그·같은 최종 조건은 기존 엔진과 같은 상품·순위·금액을 반환한다.
- 주는 사람/받는 사람 귀속, 수령인 변경, 모호한 예산, 알레르겐 누락이 테스트에서 섞이지 않는다.
- 한 턴 사용자 질문은 최대 1개이며, 확인 전 상태는 변경하지 않는다.
- 선택된 모든 역할과 실제 호출 수가 관측 정보와 일치한다. 미선택 역할은 호출하지 않는다.
- 단계 실패·JSON 오류·시간 초과·중도 취소 때 기존 세션을 보존하고 이후 늦은 결과를 적용하지 않는다.
- 실제 공급자와 기존 앱 화면에서도 요청→선택→분석→검증→질문/추천 흐름을 확인한다.

단일 추출기와 새 구조는 같은 입력·상태·카탈로그로 비교한다. 조건 추출 정확도, 귀속 오류, 제약 위반, 질문 수, 추천 일치, 논리/HTTP 호출 수, 토큰, 단계별·전체 지연, 실패율을 측정한다. 다중 에이전트가 더 좋다는 결론은 비교 결과로 판단한다. 비용·지연만 늘고 해석 품질이 개선되지 않으면 기본 `single` 모드를 유지한다.
