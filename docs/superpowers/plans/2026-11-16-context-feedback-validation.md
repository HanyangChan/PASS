# 상황별 피드백 수정 및 추천 검증 계획

작성: 2026-11-16. 분석 기준: PASS-rules, feat/rules-feedback-history, c55d9a4.
이 문서는 원인 조사와 실행 계획이다. 추천 코드·기존 테스트·환경설정은 변경하지 않았다. 다른 worktree, 운영 DB, 원격 저장소는 변경하지 않았다.

## 1. 확인한 문제

사용자 제보의 실제 계정 데이터와 화면은 아직 재현하지 않았다. 다만 상황이 달라도 과거 피드백 때문에 동일한 상위 3개가 나오는 경로를 합성 카탈로그와 실제 엔진으로 재현했다. 모든 상황에서 반드시 같은 상품이 나온다고 일반화하지 않는다.

### 코드로 확인한 원인

1. `mobile/src/chatHistory.ts:22`의 rankingFeedback은 모든 대화 기록을 합친 뒤 상품 ID별 최신 값만 남기고 `{giftId, helpful}`로 축약한다. 수령인·상황·평가 당시 조건은 전달하지 않는다. 한 상황의 최신 평가가 다른 상황의 평가도 덮어쓴다.
2. `mobile/src/cardFeedback.ts`는 대화 ID·상품·이유·시각은 저장하지만 평가 순간의 수령인·기념일·조건을 저장하지 않는다. 대화의 마지막 수령인만 이용하면 중간에 수령인이 바뀐 평가를 잘못 귀속할 수 있다.
3. `lib/engine.mjs:62`에서 과거 피드백 점수를 현재 선호와 같은 explicitScore에 더한다. 앱 정렬은 이 값을 수령인·상황 적합도보다 먼저 비교한다(:82). 점수 상한 ±2만으로 우선순위 문제를 막을 수 없다.
4. 카테고리 전체에 가산점이 붙고, 그 안에서는 리뷰·가격·ID에 따른 결정적 정렬이 반복된다. 차 두 개에 대한 긍정 평가가 평가하지 않은 차까지 올린다.
5. UI의 접근성 문구는 '추천 이유가 도움이 됐어요/안 됐어요'다(`mobile/App.tsx:837`, :846). 이 평가를 상품·카테고리 선호로 해석하고 있다. 설명에 대한 불만이 상품 비선호와 같지는 않다.
6. 현재 테스트는 '피드백으로 순위가 변한다', '금지·예산 조건은 유지된다'를 검사하지만, 상황이 바뀔 때 과거 피드백의 영향이 사라지는지 검사하지 않는다. 기존 시나리오 실행기도 기본적으로 피드백 없는 경로다.

### 최소 재현 결과

합성 상품 8개: 차 3개, 시계 3개, 생일 태그 꽃 1개, 수험 태그 문구 1개. 모든 상품 40,000원, 배송비 0, 예산 50,000원. 과거 평가는 차 2개 긍정·시계 2개 부정이다. UTF-8 입력으로 실제 `recommend`와 `APP_RANKING`을 실행했다.

| 현재 조건 | 피드백 없음 Top 3 | 과거 피드백 있음 Top 3 |
|---|---|---|
| 어머니 생일 | flower, tea-1, tea-2 | tea-1, tea-2, tea-3 |
| 친구 수험 | exam, flower, tea-1 | tea-1, tea-2, tea-3 |
| 아버지 생일, 시계 선호 명시 | watch-now, watch-old1, watch-old2 | tea-1, tea-2, tea-3 |

마지막 행은 현재 명시한 시계 선호 +3이 과거 시계 카테고리 -2와 합쳐져 +1이 되고, 차의 과거 +2보다 뒤로 밀리는 사례다. 예산·알레르기 필터를 우회하는 버그와는 구분한다.

## 2. 수정 정책

### 우선순위

예산·배송·제외 조건 등의 필수 제약 → 현재 명시한 품목·선호 충족 → 현재 수령인·상황 적합도 → 관련된 상품 선호 피드백 → 인기 등 기존 동점 기준.

가중치만 조금 낮추는 방식은 충분하지 않다. 현재 선호·상황에 대한 적합도 등급이 다른 후보를 피드백이 뒤집지 못하도록 순위 비교 항목을 분리한다. 같은 적합도 등급 안에서만 개인화를 적용하는 보수적 정책부터 검증한다. 후보가 없을 때는 관련 없는 피드백으로 빈자리를 억지로 채우지 않는다.

### 평가 의미 분리

- `reason_helpfulness`: 설명의 도움 여부. 설명 품질 분석에만 사용하며 상품 순위에 반영하지 않는다.
- `gift_preference`: 해당 상황에서 이 상품이 좋은지에 대한 명시적 평가. 상황이 맞는 경우에만 순위에 사용한다.
- 기존 helpful 기록은 화면·분석에 보존하되 상품 선호로 자동 변환하지 않는다. 의미·상황이 없는 과거 기록은 순위에 재사용하지 않는 것이 기본안이다.
- UI의 질문·접근성 문구와 실제 사용 목적을 일치시킨다. 평가 종류를 늘려야 한다면 기존 설명 평가는 유지하고 상품 적합성 질문을 별도로 둔다.

### 피드백 상황 저장 및 선택

- 평가 시점의 조건 스냅샷을 저장한다: 명시적으로 식별된 대상, 기념일, 품목·선호, 예산과 배송비 포함 여부, 카탈로그 출처, 평가 종류·시각·스키마 버전.
- 대화 ID는 추적용이며 수령인 ID를 대신하지 않는다. '친구'가 같다는 이유로 같은 인물로 단정하지 않는다. 수령인 식별이 불명확하면 대화 범위에 한정한다.
- 새 대화·수령인·기념일·품목 변경 후 관련성을 다시 판정한다. 취소된 평가·중복·반대 평가도 같은 상황 안에서만 정리한다. 상품 키는 출처와 ID를 함께 사용한다.
- 현재 명시한 선호에 반하는 과거 부정 평가는 현재 요청을 이길 수 없다. 오래된 평가 감쇠와 카테고리 일반화는 필수 수정 후 별도 실험으로 판단한다. 초기에는 개별 상품 신호부터 제한적으로 적용한다.
- 과거 평가 사용을 끄고 해당 평가를 해제할 수 있게 하며, 실제 적용한 피드백의 근거를 설명과 일치시킨다. 적용되지 않은 과거 기록을 '반영'이라고 표시하지 않는다.

### 실행 경로 정합성

- 상황 선택은 이번 발화를 해석한 **후의 조건**을 기준으로 한다. 발화 전 수령인으로 피드백을 골라 보내면 같은 요청에서 대상을 바꿀 때 다시 섞일 수 있다.
- 게스트·서버 A~D가 같은 선택·순위 정책을 공유하게 한다. 서버는 확장된 피드백 형식·크기·값을 검증한다.
- App.tsx의 refreshSignal은 ref와 React 상태를 갱신하지만, 현재 실행 중인 게스트 chatService는 이전 렌더에서 만든 객체일 수 있다. 첫 후속 요청부터 새 피드백이 적용되는지 별도 재현하고, 요청당 불변 스냅샷을 전달하는 구조로 정리한다. 이것은 추가 확인 대상이며 확정된 버그로 간주하지 않는다.
- 일반 추천과 가상 예산 비교는 동일 정책을 사용한다. 가상 비교 중 수령인·실제 예산·피드백 저장값을 변경하지 않는다.

## 3. 구현 순서와 변경 범위

1. 재현을 회귀 사례로 고정하고, 현 코드에서의 조건·후보·상위 3개·점수 항목을 저장한다.
2. 설명 도움 평가를 상품 순위 신호에서 분리한다. 과거 기록은 삭제 없이 보존하고 알 수 없는 형식은 순위 적용에서 제외한다.
3. 평가 시점의 상황 스냅샷과 새 스키마를 도입한다. 로컬·가짜 계정 DB에 이전 형식과 새 형식을 함께 넣어 복원·저장을 검사한다.
4. 상황 선택 함수와 순위 우선순위를 공통화하고, 앱용 명시적 옵션에서 활성화한다. 공용 엔진의 옵션 없는 기본 동작을 임의 변경하지 않는다.
5. UI의 의미·표시와 게스트/서버 요청 스냅샷을 맞춘다.
6. 아래 검증을 통과한 뒤 변경 내역·실패 사례·잔여 한계를 보고한다. push·PR·merge·배포는 별도 사용자 승인 전 수행하지 않는다.

예상 파일: `mobile/src/cardFeedback.ts`, `chatHistory.ts`, `services/{feedbackRepository,cloudRecords,chatService,serverChatService}.ts`, `mobile/App.tsx`, `api/worker.mjs`, `lib/engine.mjs` 및 관련 테스트. 새 정책은 공통 순수 함수로 분리한다. lib와 vendor가 공유하는 코드를 수정하면 vendor를 LF로 동기화하고 해당 provenance 해시를 갱신한다. 기존 '향수 말고 커피' 합의와 다른 에이전트 기본 동작은 유지한다.

## 4. 추천 검증 설계

### A. 조건 추출과 순위를 분리

- 자연어 해석: 문장 → 기대 조건·질문을 비교한다. 특히 수령인 변경·부정·품목 변경·배송비·예산 가정을 포함한다.
- 순위: 사람이 미리 정한 조건을 직접 엔진에 입력한다. 파서가 틀린 경우와 랭커가 틀린 경우를 분리한다.
- 저장·화면: 엔진이 맞아도 오래된 화면·다른 계정 피드백이 표시되는 경우를 별도로 검사한다.

### B. 기준선 및 재현성

- 기존 135개 대화 × amazon/web/both × 게스트/서버 A를 유지한다. 실행 시 실제 사례 수를 읽어 기록하고 135를 하드코딩하지 않는다.
- 현재 버전과 수정 버전에서 같은 상품 스냅샷·해시·기준 날짜·가격·조건·모델 설정을 사용한다. 현 실행기의 todayKst 의존성을 평가에서는 주입한 고정 날짜로 바꾼다.
- 기존 CRLF 실패는 baseline의 같은 테스트명·원인으로만 구분한다. 그 외 새 실패는 허용하지 않는다. core 152, mobile 101, router 52 등의 수치는 인수인계 기준이며 이번 턴에서 다시 통과했다고 주장하지 않는다.
- 기존 체크의 affordable/nameOk는 상품값만 보며 배송비·재고·제외 조건 등을 모두 반영하지 않는다. '적합 후보가 있다'는 판정도 독립된 전체 제약 검증으로 보강해야 한다. 추천 엔진 자체 출력을 정답으로 재사용하지 않는다.

### C. 과거 피드백 교차 평가

서로 다른 적합 후보가 충분한 12개 상황을 먼저 선정한다. 예: 어머니 생일 차, 아버지 생일 시계, 친구 수험 문구, 연인 기념일 꽃, 부모님 명절, 직장 감사 등. 각 상황에 다음 6가지 기록을 적용한다.

1. 기록 없음.
2. 같은 대상·같은 상황의 상품 선호.
3. 다른 대상의 상품 선호.
4. 같은 대상이지만 다른 상황·품목의 선호.
5. 현재 선호와 반대되는 과거 평가 및 특정 카테고리에 집중된 평가.
6. 설명 도움 평가만 있거나 상황이 없는 이전 형식 기록.

12 × 6 = 72개 평가 과제. 카탈로그 3종 × 경로 2개로 버전당 432회 실행한다. 각 셀의 기대 후보·허용 범주를 먼저 정하고, 후보 부족 셀은 억지 정답 대신 별도 표기한다. 소형 합성 카탈로그로 정확한 순위를 검사하고 실제 카탈로그로 상품명 규칙의 한계를 확인한다. 반복 노출만으로 임의 상품 교체를 요구하지 않는다.

### D. 기록·화면 검증

운영에 접속하지 않는 데이터가 채워진 가짜 DB와 `https://pass-mock.test`를 사용한다.

- 사용자 A/B와 게스트 기록 분리, 로그아웃·로그인·복원·새 대화.
- 한 대화에서 수령인과 상황이 바뀐 뒤 평가, 저장 후 재진입.
- 👍→👎→취소, 평가 기록 해제, 대화 삭제 뒤 적용 신호 제거, 이전 스키마 복원.
- 피드백 직후 첫 요청·두 번째 요청·페이지 재진입 결과의 일치.
- 저장 실패·재시도·늦은 응답·계정 전환 도중 요청의 무효화.
- 화면 카드·추천 이유·지난 대화·API 반환 상품이 같은 실행 결과인지 확인.
- A~D는 결정적 모델 모형으로 공통 정책을 검증한다. 실제 모델의 정확도·시간·비용 측정은 별도 실행 범위로 둔다.

같은 조건·같은 카탈로그에서 결과가 같은 것은 정상이다. 서로 다른 정답 범주를 요구하는 상황에서도 같은 결과가 고착되는지를 실패로 본다. 후보가 1~2개인 경우와 여러 적합 후보가 있는 경우를 나눠 반복률을 해석한다. 상품명만 다른 동일 상품 변형도 따로 집계해 다양성을 부풀리지 않는다.

### F. 사람의 적합성 평가

자동 테스트는 가격 계산·정책 준수를 검증하지만 선물로 좋은지는 증명하지 않는다. 수정 후 개발에 쓰지 않은 새로운 문장을 따로 보관하고, 실제 카탈로그의 상위 3개를 평가자 2명이 버전 정보를 가린 채 독립 평가한다. 대상·상황 적합성, 현재 요구 충족, 부적합 이유를 상품별 0~2점으로 기록하고 불일치도 보고한다. 개발용 합성 재현 점수와 이 결과를 섞지 않는다. 사용자 만족도·선택 성공은 후속 사용자 과제로 검증하며 소규모 점검을 일반 정확도로 표현하지 않는다.

## 5. 실행 산출물

- 재현 입력과 수정 전/후 Top 3, 필수 제약 통과 여부, 점수 분해.
- 버전·카탈로그 해시·날짜·경로·피드백 적용/제외 사유가 있는 평가 JSON.
- 432개 교차 실행 결과와 기존 회귀 결과, 실패 사례 원문 및 원인 분류.
- 데이터가 채워진 가짜 계정 DB 및 게스트의 화면 점검 결과.
- 자동 검사 통과 범위와 사람 평가를 분리한 검증 보고서.

이 계획 작성 시 수행한 검증은 코드 읽기와 합성 3상황 재현이다. 전체 회귀·실제 사용자 제보 데이터 재현·실계정·유료 모델 호출·운영 변경은 수행하지 않았다.
