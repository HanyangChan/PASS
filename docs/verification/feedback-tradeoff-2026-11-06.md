# 피드백의 시간·정확도 트레이드오프 · 2026-11-06

같은 B 행동 모델과 도구 런타임에 검토·수정 루프를 추가해 실제 공급자로 비교했다. 새 문구 과제에서 평균 응답 시간이 약 두 배로 늘면서 과제 성공률이 상승했다. 그러나 검토 상한을 1회에서 2회로 높인 효과는 모든 과제에서 일관되지 않았으며, 첫 검토가 잘못 통과시키는 오류도 남았다.

## 실험 설계

- 비교: B 그대로, 행동당 검토 최대 1회, 행동당 검토 최대 2회. 검토가 수정 요구를 반환하면 같은 행동 모델에 구체적 피드백을 전달하고 다시 행동을 선택한다. 2회 모드의 추가 검토는 첫 검토가 지적했을 때만 수행한다.
- 기존 20개 과제는 회귀 확인용 각 1회, 새 문구 10개는 각 3회. 각 모드 50개 과제 실행·52개 API 요청, 전체 150개 과제 실행·156개 API 요청이다. 기대 상태·정답·채점 결과는 모델에 전달하지 않았다.
- 새 문구 과제는 피드백 실측 전에 고정했다. 같은 과업 유형의 내부 평가이며 외부 비공개 평가셋은 아니다. 검토 설계에는 앞선 A/B 실패 유형이 반영되어 있으므로 기존 과제 개선과 새 문구 결과를 구분한다.
- 모두 deepseek-v4-flash, temperature 0, reasoning=false, 같은 초기 상태와 고정 상품 3,376개, 같은 공통 추천 엔진을 사용했다. 과제별 모드 실행 순서와 반복별 과제 순서를 순환했다.
- 기존 B의 LLM 상한은 6회, 피드백 모드는 행동·검토·수정을 합해 10회다. 전체 실행 20초·도구 5회 상한은 같다. 따라서 피드백과 추가 계산 예산을 함께 제공한 운용 모드의 비교다. 같은 총 계산량에서 검토의 순수 효과를 분리한 실험은 아니다.
- 검토 중에는 에이전트 코드를 고치지 않았다. 저장한 소스 해시가 실험 종료 시점의 코드와 일치함을 확인했다.

## 새 문구 평가 · 주 결과

10개 문구 × 3회 = 모드별 30회. 시간은 요청 1회 기준이며 실패도 포함한다. 정확도는 조건 반영·보존, 올바른 질문, 추천·금액·비교 결과를 모두 만족하는 과제 성공률이다.

| 모드 | 성공률 | 평균 | 중앙값 | p95 | 평균 LLM 호출 | HTTP 오류 |
| --- | --- | --- | --- | --- | --- | --- |
| B · 피드백 없음 | 86.7% (26/30) | 1.28초 | 1.18초 | 1.94초 | 1.67회 | 4회 |
| B + 최대 1회 검토 | 93.3% (28/30) | 2.64초 | 2.50초 | 5.57초 | 3.43회 | 2회 |
| B + 최대 2회 검토 | 100.0% (30/30) | 2.62초 | 2.49초 | 4.12초 | 3.87회 | 0회 |

B → 최대 2회 모드에서 평균 1.33초를 더 쓰고 성공률이 13.3%p 높아졌다. 시간은 2.04배, LLM 호출은 2.32배였다.

최대 1회와 2회 모드의 평균 시간은 2.64초와 2.62초로 비슷했다. 2회 모드는 처음부터 두 번 검사하지 않으며, 네트워크·생성 지연 변동도 섞인다. 이 작은 평균 차이를 2회 모드의 속도 우위로 해석하지 않는다. 2회 모드가 실제 LLM 호출은 더 많이 사용했다. 두 점을 단조로운 연속 곡선이라고 가정하지 않는다.

## 기존 과제 회귀 확인

앞선 비교에서 사용한 20개 과제를 이번 실행에서 다시 1회씩 평가했다. 과거 A/B 측정치를 합친 결과가 아니다.

| 모드 | 전체 성공률 | 인사/감사 제외 업무 성공률 | 평균 응답 시간 |
| --- | --- | --- | --- |
| B · 피드백 없음 | 80.0% (16/20) | 83.3% (15/18) | 1.30초 |
| B + 최대 1회 검토 | 95.0% (19/20) | 100.0% (18/18) | 2.41초 |
| B + 최대 2회 검토 | 90.0% (18/20) | 94.4% (17/18) | 2.41초 |

최대 1회 모드는 기존 취향 귀속 오류를 확인 질문으로 바꾸고, 종료 계약에 맞게 행동을 수정한 사례가 있었다. 반면 최대 2회 모드는 “나는 커피를 좋아해”를 어머니 취향으로 적용한 행동을 검토가 통과시켜 오류가 남았다. 세 모드 모두 감사에 대한 일반 확인 응답은 지정한 감사 문구 채점 기준에 미달했다. 감사 문구 실패는 사실·상태 오류와 구분해야 한다.

## 해석

이번 결과는 B의 빠른 경로와 검토를 추가한 더 정확한 경로 사이에 관측된 시간·성공률의 교환관계를 보여준다. 새 문구 평가에서는 최대 2회 모드가 더 유리한 정확도 운용점이었지만, 기존 회귀 평가에서는 최대 1회 모드보다 성공률이 낮았다. “더 반복하면 언제나 더 정확하다”는 결론은 지원하지 않는다. 오류 비용이 큰 조건 변경·귀속 판단 등에 검토를 선택적으로 적용하는 방식은 후속 실험 후보이며 이번에는 측정하지 않았다.

- 새 문구의 독립 종류는 10개이며 반복 30회를 30개의 서로 다른 과제처럼 해석하지 않는다. 30/30 성공이 일반적 100% 정확도를 뜻하지 않으며 통계적 유의성은 검증하지 않았다.
- 실제 API 핸들러·공급자 네트워크·공통 엔진을 측정했다. 실제 인증·운영 DB 조회·브라우저 렌더링은 제외했다. 인증·계정·세션은 합성 대체물이고 사용자 데이터는 변경하지 않았다.
- 최종 응답은 기존 B처럼 엔진 근거 또는 대화 템플릿이다. 별도의 문장 품질 평가, 독립 Planner, 전체 전략 재계획 구현까지 포함하지 않는다.
- 한도 1회 모드의 수정 행동은 추가 모델 검토 없이 서버 검사로 넘어갈 수 있다. 2회 모드도 첫 검토가 오류를 잘못 통과시키면 재검토를 하지 않는다. 모델 검토는 결정적 검증을 대체하지 않는다.
- baseline 83개·API 40개 자동 검사 및 Worker 배포 없는 빌드를 통과했다. 기존 B 기본 선택과 운영 배포는 변경하지 않았다.
