# A 혼합 조건 요청 실패 수정

화면의 ‘친구 생일 선물…10만 원…실용적인 걸 좋아해’ → ‘향이 강한 제품은 빼고, 먹는 것도 제외해줘.’ → ‘배송비 포함’을 합성 인증·합성 세션·합성 카탈로그로 실제 공급자에 재현했다. 사용자 저장 기록은 변경하지 않았다.

## 재현 결과

- 수정 전 추론 설정 생략: 최초 조건과 혼합 제외 요청 모두 HTTP 503. 공급자는 HTTP 200을 반환했지만 `finish_reason:length`, 본문 없음, 1,600 completion 토큰 전부 reasoning 토큰이었다. 네트워크 연결 실패나 사용자 요청 거부가 아니라 응답 생성 한도 소진이었다.
- 수정 전 추론 비활성: HTTP 200이지만 배송비가 미정인 상태에서 혼합 제외 요청의 음식 제외가 적용되지 않았다. 해석 결과의 확인 질문 때문에 A가 변경을 롤백하는 경로였다.
- 수정 후 설정 생략/명시적 false 모두 3턴씩 HTTP 200. 최초 수령인·생일·10만원 반영, 혼합 제외 요청은 LLM 없이 음식/간식/커피·차/건강식품 제외 반영 및 향 한계 안내, 배송비 답장 뒤 제외 유지·정상 결과 반환.

원문: `router-mixed-before-2026-11-06.json`, `router-mixed-after-2026-11-06.json`.

## 변경

- A의 단일 조건 추출에서 DeepSeek 모델은 추론 옵션 미지정 시 false를 기본값으로 사용한다. 명시적인 true/false 설정은 존중한다. 설정 파일의 키나 공급자를 변경하지 않았다.
- A 규칙 해석기에 명시적인 먹는 선물 제외와 알려진 향 정보 한계를 추가했다. 둘을 함께 입력해도 지원되는 제외는 적용하고 배송비 등 필수 미정 조건만 이어서 묻는다. 향을 근거 없는 전체 화장품/홈데코 제외로 바꾸지 않는다.
- 앱은 화이트리스트 서버 오류 코드로 AI 처리 실패·상품 로드 실패·연결 실패를 구분한다. 공급자 원문 오류는 표시하지 않고 입력/상태 보존을 유지한다.
- ‘실용적’ 선호는 현재 평가 태그가 없어 구체적인 선호로 저장하지 않는다. 향 강도 필터도 구현한 것이 아니라 한계를 안내한다.

검증: 코어 105, baseline 90, API 45, 모바일 79개 테스트 통과. A 실행 예제, 모바일 lint/typecheck 검증. 합성 카탈로그가 식품 위주라 음식 제외 후 빈 결과는 정상이다. 실제 브라우저 로그인/사용자 DB 검증이나 A/B/C 성능 재측정은 아니다. 이전 비교 수치는 변경 전 설정의 기록이다.

재현: `node api/diagnostics/router-mixed-conditions.mjs <결과.json>` (실제 공급자 사용량 발생)。
