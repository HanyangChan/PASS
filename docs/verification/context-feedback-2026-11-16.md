# 상황별 상품 평가 수정 및 검증 결과

후속 새 문장·LLM 상품 적합성 평가와 추가 수정은 [후속 보고서](unseen-and-llm-gift-review-2026-11-16.md)에 기록했다. 이 문서는 첫 피드백 수정 단계의 역사적 결과다.

2026-11-16 · PASS-rules / feat/rules-feedback-history · 기준 커밋 c55d9a4.
이 결과는 커밋 전 로컬 변경에 대한 기록이다. 원격 push·PR·merge·배포·운영 DB 변경은 하지 않았다.

## 변경한 동작

- 이전 설명 도움 평가를 상품 선호로 해석하던 연결을 끊었다. 기존 기록은 보존한다.
- 카드에 '설명 평가'와 '이 상황의 선물 평가'를 분리했다. 새 상품 평가는 평가 당시 조건, 대화 범위, 출처별 상품 키를 저장한다.
- 같은 대화·같은 수령인/기념일/선호/예산/배송비/제외/포장/마감 조건의 평가만 적용한다. '친구'처럼 라벨이 같다는 이유로 다른 대화의 인물을 연결하지 않는다.
- 상품 선호는 현재 명시 요청, 예산·제외 조건, 상황 적합도보다 후순위인 개별 상품 동점 조정(+1/-1)이다. 카테고리 전체를 올리지 않는다.
- 입력을 해석한 후의 조건으로 적용할 평가를 고른다. 첫 후속 요청부터 최신 평가를 읽도록 게스트 경로의 요청 스냅샷을 고쳤다.
- 설명 평가와 상품 평가는 별도로 취소할 수 있다. 같은 평가를 다시 누르면 취소되며 전체 상품 평가 사용도 다음 추천부터 끌 수 있다.
- 계정의 현재 대화를 복원하면 평가 당시 상황도 함께 복원한다. 대화의 최종 수령인으로 과거 평가를 다시 귀속하지 않는다.
- 공통 엔진은 contextualFeedback 옵션으로 분기하고 앱 APP_RANKING에서 활성화했다. 옵션 없는 기본 동작과 명시적 legacy 옵션은 유지했다. vendor를 LF로 동기화하고 provenance 해시를 갱신했다.

수령인 고유 ID가 없는 현재 구조에서 대화 간 자동 취향 재사용은 제공하지 않는다. 현재 대화의 저장·복원과 다른 대화의 장기 개인화는 구분해야 한다. 예산 변경도 다른 평가 상황으로 취급하는 보수적인 정책이다.

## 원인 재현과 수정 후 확인

실제 엔진에 합성 상품 8개와 '차 2개 긍정, 시계 2개 부정' 기록을 넣었다. 수정 전에는 어머니 생일·친구 수험·아버지 시계 선호에서 모두 같은 차 3개가 나왔다.

회귀 검사에서는 현재 시계 선호를 과거 차 평가가 덮어쓰지 않는지, 생일·수험 적합도를 보존하는지, 무관한 수령인/상황/설명 평가/이전 형식 기록에 대해 결과가 그대로인지 검증했다. 같은 적합도의 후보 사이에서는 관련 개별 상품 선호가 실제로 순위를 바꾸는지도 검사했다. 후보가 품절되어 평가 대상에서 빠진 경우에도 나머지 결과를 바꾸지 않는다.

## 고정 카탈로그 교차 검증

`scripts/verify-context-feedback.mjs`로 12상황 × 6기록 유형 × 3카탈로그 × 2경로 = 432회 실행했다. 기준 날짜는 2026-11-16으로 고정했다. 인증은 https://pass-mock.test의 모형이며 외부 모델·운영 계정·운영 DB는 사용하지 않았다. 엔진과 vendor 소스 해시가 실행 시작부터 종료까지 일치하는지 확인했다.

| 항목 | 결과 |
|---|---|
| 수정 후 필수 제약/현재 품목/무관한 기록/경로 일치 검사 | 432회 중 위반 0 |
| 수정 전 정책 비교 | 216개 조건 중 69개에서 현재 품목 무시 또는 무관한 기록에 의한 순위 변화 |
| 서로 다른 상황의 Top 3 평균 Jaccard 겹침 | 수정 전 0.0940 → 수정 후 0.00539, 동일 카탈로그·기록 유형 내 1,188쌍 |
| Top 1 최대 집중 비율 | 9.26% → 5.56% |
| 고유 Top 1 상품 수 | 27 → 40 |
| 전체 Top 3에 등장한 고유 상품 수 | 95 → 77 |

수정 전은 HEAD의 엔진을 별도 폴더에 복원하고 기존의 helpful → 전역 카테고리 가중 변환을 적용한 결과다. 수정 후는 실제 게스트 서비스와 Worker 핸들러를 각각 실행했다. 따라서 수정 전 정책 비교 단위는 216개 조건이고, 수정 후 실행 단위는 경로를 포함한 432회다. 일반 사용자 정확도나 추천 품질 100%라는 의미가 아니다. 이 12상황은 개발자가 만든 내부 과제이고 각 카탈로그의 품질·구성도 통제된 사용자 연구가 아니다.

고유 상품 수가 줄어든 점도 함께 보고한다. 무관한 후보가 사라지고 Top 1 집중이 줄었다는 관측을 전체 다양성 개선으로 일반화하지 않는다. 같은 조건에서 같은 적합 상품이 반복되는 것은 정상이며 무작위로 결과를 바꾸지는 않는다.

### 카탈로그 부족

- Amazon의 수험 문구·생일 꽃 과제 2개에는 지정 예산과 제약을 만족하는 해당 상품군 후보가 없었다. 기록·경로 반복을 포함하면 24회다.
- 한국 웹 카탈로그의 아버지 시계 과제까지 포함하면 원하는 상품군 후보 3개 미만인 조합은 36회다.
- 해당 항목은 후보 부족으로 따로 표시했고 존재하지 않는 정답 상품을 요구하지 않았다. 이 항목까지 '원하는 상품 추천 성공'이라고 계산하지 않는다. 카탈로그 보완 및 대안 안내 품질은 후속 검증 대상이다.

## 재실행 및 산출물

저장소 루트에서 Node 22.13 이상으로 실행한다.

```sh
node --experimental-strip-types scripts/verify-context-feedback.mjs
node --experimental-strip-types --test tests/context-feedback.test.mjs mobile/tests/context-feedback.test.mjs api/tests/feedback-ranking.test.mjs
```

브라우저 검증은 먼저 별도 터미널에서 환경파일 로드를 끄고 가짜 설정을 지정한 Expo를 포트 8771로 실행한다. Windows PowerShell의 예시는 다음과 같다.

```powershell
$env:EXPO_NO_DOTENV='1'
$env:EXPO_PUBLIC_SUPABASE_URL='https://pass-mock.test'
$env:EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY='sb_publishable_synthetic'
$env:EXPO_PUBLIC_CHAT_API_URL='http://127.0.0.1:18788'
$env:EXPO_PUBLIC_CATALOG_SOURCE='amazon'
$env:CI='1'
npm --prefix mobile run web -- --port 8771 --offline --max-workers 2
```

다른 터미널에서 `node --experimental-strip-types scripts/verify-feedback-ui.mjs`를 실행한다. API 주소 18788은 실제 서버를 켜지 않고 브라우저 검사에서 가로채 실제 Worker 핸들러와 가짜 인증으로 처리한다. 기본 브라우저는 로컬 Edge이며 `PASS_BROWSER`로 실행 파일 경로를 지정할 수 있다. CI 모드에서는 앱 소스를 바꾼 뒤 Expo를 재시작해야 한다.

- 전체 실행 결과·조건별 점수·카탈로그 및 소스 해시: `work/context-feedback/evaluation.json`
- 최종 회귀·타입·린트 등 원문 로그: `work/context-feedback/logs/`
- 화면 결과와 캡처: `work/context-feedback/ui/results.json`, `guest.png`, `account.png`
- 평가자 2명용 빈 자료: `work/context-feedback/human-evaluation.json` (72묶음)
- 버전 대응 키: `work/context-feedback/human-evaluation-key.json` (평가자에게는 제공하지 않음)

**사람의 선물 적합성 평가와 독립된 새 문장 평가는 아직 남아 있다.** 빈 평가 자료는 수행한 사람 평가가 아니며 개발 과제의 블라인드 검토 자료다. 재사용하지 않은 독립 문장·평가자 모집과 실제 사용자 과제는 별도로 수행해야 한다.
