# 모든 채팅을 처리하는 Agent 비교안

상태: B안의 기본 전체 채팅 Agent와 API 연결은 [full-chat 구현](../../baseline/agents/full-chat/README.md)에 추가했다. [full-chat-feedback](../../baseline/agents/full-chat-feedback/README.md)에 행동 검토 → 수정 → 재검토의 제한된 루프와 API 선택 모드를 추가했다. 아래의 독립 Planner·전체 전략 재계획·문장 초안 수정까지 모두 구현한 것은 아니다. 운영 배포는 포함하지 않는다.

## 비교 목적과 범위

현재 규칙 우선 Router는 정해진 경로를 우선 처리하고 필요한 부분에 LLM을 연결한다. 이 비교안은 추천·조건 수정·질문 답변·추천 이유·예산 비교·일반 대화 등 **모든 사용자 발화를 같은 에이전트 진입점에서 처리**한다. 간단한 인사도 에이전트가 직접 답변할 수 있으며, 모든 발화에 상품 검색을 강제하지 않는다. 화면 열기·스크롤·카드 펼치기는 채팅 발화에 포함하지 않는다.

에이전트가 다음 행동과 종료를 선택하되 인증·도구 권한·조건 검증·금액 계산·저장 처리는 서버가 집행한다. 기존 PASS 엔진과 같은 상품 DB를 사용한다. 에이전트가 상품·가격·순위를 임의로 생성하지 않는다.

Planner, 실행 Agent, Reflection, 응답 검토는 논리적 역할이다. 초기 구현에서는 같은 모델과 런타임으로 순차 호출할 수 있으며 별도 서버나 병렬 다중 에이전트를 전제하지 않는다. 계획은 작업 목록·선택한 도구·성공 조건으로 기록하고 내부 추론 원문은 저장하지 않는다.

## 추가하는 피드백 루프

| 루프 | 돌아가는 조건 | 돌아가는 위치 | 다음 행동 |
| --- | --- | --- | --- |
| 조건 확인 | 사용자 조건 충돌 또는 필수 정보 누락 | 사용자에게 질문 후 턴 종료 | 다음 발화에서 메모리를 복원하고 재판단 |
| 도구 수정 | 스키마 오류·유효하지 않은 상품 ID | 행동 선택 | 오류 항목만 수정하고 허용 범위 내 재호출 |
| 근거 보강 | 후보는 있으나 속성·설명 근거 부족 | 행동 선택 | 상품 근거 조회 또는 다른 도구 선택 |
| 전략 재계획 | 후보 없음·도구 결과가 목표를 충족하지 못함 | Planner | 실패 원인을 반영해 작업 순서를 수정 |
| 응답 재검토 | 표현 누락·구성 오류 | 답변 수정 | 지적 사항을 고친 뒤 다시 검증 |
| 응답에서 실행 복귀 | 근거 부족 또는 목표·조건 불일치 | 행동 선택 또는 Planner | 필요한 도구를 실행하거나 계획을 수정 |

제약 검사·상품 ID·금액·상태 버전은 서버의 결정적 검사로 판정한다. 요청 충족·설명 누락은 LLM 검토로 보완한다. 검토 모델이 통과시켜도 서버 제약 검사를 우회할 수 없다. 단순 응답은 기본 검증으로 종료하고, 추천·비교 또는 검증 실패가 있을 때 상세 검토를 호출한다. 역할별 LLM 호출 횟수는 로그에 따로 남긴다.

## 반복 종료 정책

다음 값은 측정 전 제안값이며 달성된 성능이나 최적 설정을 의미하지 않는다. 루프마다 한도를 새로 부여하지 않고 사용자 한 턴의 공통 카운터를 쓴다.

| 제한 | 초기 제안 |
| --- | --- |
| 전체 LLM 호출 | 최대 10회, Planner·조건 추출·검토·수정 호출 모두 포함 |
| 전체 도구 호출 | 최대 5회, 실패·재시도 포함 |
| 재계획 | 최대 2회, 최초 계획 제외 |
| 초안 수정 | 최대 2회, 수정 후 재검증도 전체 LLM 한도에 포함 |
| 일시적 조회 오류 | 동일 호출 재시도 최대 1회 |
| 서버 실행 시간 | 최대 30초, 실제 모델 지연에 맞춰 실험 전 고정 |
| 진행 정체 | 상태·도구·인자가 같고 새 근거 없는 반복이 2회 연속이면 종료 |

모든 재진입 전 공통 예산을 검사한다. 하나라도 소진되면 검증된 결과만 반환하거나 필요한 확인 질문 하나를 반환하고 종료한다. 종료 안내에는 별도 LLM 호출이 필요 없는 서버 템플릿을 사용한다. 확인 질문을 보낸 뒤에는 내부 루프를 계속 실행하지 않는다. 사용자의 다음 발화는 새 턴이지만 같은 미해결 질문과 상태를 이어받는다.

에이전트가 제안한 예산 증액·제외 조건 완화는 복제된 상태에서만 비교한다. 명시적 적용 전 실제 상태를 바꾸지 않는다. 도구 결과가 현재 상태 버전과 다르면 기존 결과를 폐기하고 남은 예산 내에서 재조회하거나 종료한다.

## 복합 요청의 예시 실행

아래는 설계를 설명하기 위한 가상 실행이며 실제 상품 검색 결과가 아니다.

사용자: “부모님 두 분께 드릴 선물 추천해줘. 총 10만 원, 배송비 포함이고 견과류는 빼줘. 없으면 12만 원도 비교하고 추천 이유까지 알려줘.”

1. 확인된 조건을 구조화하고 목표를 ‘10만 원 후보 확인 → 필요하면 12만 원 가상 비교 → 근거 설명’으로 잡는다. 추가 필수 정보가 없다는 가정이다.
2. 검색 결과 후보가 없으면 Reflection이 ‘현재 조건에서 후보 없음’을 기록한다.
3. Planner가 사용자가 허용한 12만 원 가상 비교로 계획을 수정한다. 실제 예산은 10만 원을 유지한다.
4. 비교 후보가 나오지만 성분 근거가 부족하면 실행 Agent로 돌아가 상품 근거를 조회한다.
5. 성분 근거가 확인되면 초안을 작성한다. 확인되지 않으면 견과류 제외를 충족했다고 확정하지 않고 질문하거나 한계를 알린다.
6. 응답 검토에서 ‘배송비 포함 총액’ 설명이 빠졌다면 초안을 수정하고 재검증한다.
7. 검증된 답변과 12만 원 적용 제안을 표시한다. 실제 예산 변경은 사용자의 명시적 적용 이후 수행한다.

각 단계는 한도 안에서만 실행한다. 예시 순서를 모든 발화에 고정하지 않으며 간단한 대화는 도구 없이 종료할 수 있다.

## 비교 실험

복잡한 반복 구조가 항상 품질을 높인다고 가정하지 않는다. 모든 발화를 에이전트로 보내는 효과와 피드백 반복의 효과를 구분하려면 다음 세 조건을 비교한다.

| 조건 | 실행 제어 | 피드백 |
| --- | --- | --- |
| A · 현재 부분 활용 | 현재 a-router의 규칙 우선 처리 | 현재 구현 그대로 |
| B · 전체 채팅 Agent | 모든 발화를 Agent가 처리 | 도구 관찰 후 행동 선택, 별도 다단계 검토 없음 |
| C · 전체 채팅 + 반복 피드백 | B와 같은 진입점 | 이 문서의 재계획·근거 보강·응답 수정 루프 |

A↔B는 실행 제어 범위 변경의 효과, B↔C는 추가 피드백의 효과를 보는 비교다. A↔C만 비교하면 두 변화의 영향을 분리할 수 없다. 세 조건은 같은 과업·초기 상태·상품 스냅샷·추천 규칙·조건 검증·도구 접근 권한·모델 버전·공통 실행 상한을 고정한다. 각 조건은 독립 세션에서 실행하고, 모델 변동을 보기 위해 시나리오별 반복 횟수를 실험 전에 정한다. 사용자 응답이 필요한 시나리오는 동일한 후속 답변을 제공한다.

측정 항목은 과업 완료율, 조건 보존 정확도, 제약 위반, 근거 없는 주장, 확인 질문 수, 턴 수, LLM·도구 호출 수, 토큰·비용, 응답 시간 p50/p95, 재계획·수정 횟수, 한도 종료율이다. 단순 대화·조건 변경·후보 없음·다중 조건 충돌·불완전 근거·예산 가상 비교·연속 수정·도구 오류를 모두 포함한다. 호출 수가 적은 요청에 반복을 강제해 복잡도를 맞추지 않는다.

검증 로그에는 `sessionId`, `turnId`, 실험 조건, 상태 버전, 단계, 도구명·검증된 인자, 근거 ID, 실패 코드, 복귀 위치, 호출 카운터, 지연시간, 종료 사유를 남긴다. 비밀값과 내부 추론 원문은 기록하지 않는다.
