# PASS LLM Agent 설계

문서화 범위: **목표 설계**. 이 README 추가는 에이전트의 구현·배포 완료를 의미하지 않는다.

[메인 README의 구조도](../../README.md#llm-agent-목표-구조) · [Mermaid 원본](architecture.mmd) · [기존 운영 아키텍처](../architecture.md) · [현재 API](../../api/README.md)

## 목적

사용자의 선물 조건을 유지하면서 필요한 질문·상품 검색·추천 이유 설명·예산 비교를 선택하는 에이전트를 만든다. LLM이 다음 행동과 도구, 종료 시점을 결정하고 도구의 관찰 결과를 바탕으로 제한된 횟수 안에서 재계획한다.

에이전트는 요청마다 실행하고 답변·확인 질문·한계 안내를 반환하면 종료한다. 화면 열기, 카드 펼치기, 대기처럼 판단이 필요 없는 UI 동작은 에이전트를 실행하지 않는다. 명시적 적용 버튼 등 결과가 정해진 동작은 검증된 서버 로직으로 처리할 수 있다.

핵심 원칙은 **추천 계산과 실행 제어를 분리**하는 것이다. LLM이 도구를 선택하더라도 상품·금액·순위는 기존 PASS 엔진의 결과를 사용한다.

## 현재 구현과 목표의 차이

| 항목 | 현재 저장소 | LLM Agent 목표 |
| --- | --- | --- |
| LLM 역할 | Gemini로 조건 추출 | 조건 해석·다음 행동 선택·응답 생성 |
| 실행 순서 | 백엔드에 정의된 흐름 | LLM이 도구와 종료 시점 선택 |
| 추천·정렬·가격 | 공통 PASS 엔진 | 같은 엔진 재사용 |
| 재계획 | 에이전트 루프 없음 | 도구 관찰·검증 결과로 제한 내 재계획 |
| 메모리 | 기존 대화·조건 상태, 기기 내 수령인 기억 | 구조화 조건 + 미해결 질문 + 도구 실행 문맥 |
| 실험 모드 | Agent/Hybrid 비교 모드 없음 | 후속 단계에서 실행 제어 방식 비교 |

현재 API의 조건 추출 LLM 호출을 완성된 Agent 또는 아래에서 정의한 Hybrid 실험 모드로 간주하지 않는다. 현재 구현 범위는 [API README](../../api/README.md)와 [수령인 기억 문서](../personalization.md)를 따른다.

## 구성 요소

각 서버 모듈은 초기에는 하나의 Cloudflare Worker 안에 둔다. 별도의 에이전트 서버나 여러 LLM 에이전트로 분리하지 않는다.

| 모듈 | 책임 |
| --- | --- |
| Core / Planning | 현재 요청·상태·도구 결과를 보고 질문, 도구 실행, 응답, 종료 선택 |
| Memory | 확인 조건, 미해결 질문, 상태 버전, 추천 ID, 도구 결과 유지 |
| Tool gateway | 허용된 도구, 입력 스키마, 실행 횟수 검증 |
| PASS engine | 상품 필터, 정렬, 금액, 가상 예산 비교 계산 |
| Reflection / Validator | 조건·금액·근거·승인 상태를 검증하고 오류·미확인 정보 반환 |
| Response validator | LLM 응답의 상품 ID·금액·주장을 도구 근거와 대조 |
| UI / Human checkpoint | 추천·변경 내용 표시, 필요한 확인과 적용·되돌리기 제공 |

Reflection은 검증 결과로 다음 행동을 조정하는 과정이며, 모델을 학습시키거나 자동으로 정확성을 보장하는 기능이 아니다. 규칙으로 검사 가능한 항목은 서버가 판정한다.

## 실행 흐름

1. 앱이 발화 또는 확인 응답을 서버에 보낸다. 서버가 인증·입력·조건 변경 후보를 검증한다.
2. 에이전트가 확인된 조건, 미해결 질문, 허용된 도구를 받아 다음 행동을 선택한다.
3. 정보가 부족하면 질문 하나를 반환하고 이번 실행을 종료한다.
4. 도구를 선택했다면 서버가 인자와 호출 제한을 검증하고 엔진을 실행한다.
5. 도구 결과와 제약 검증 결과를 에이전트에 전달한다. 추가 정보가 필요하면 허용된 범위에서 다음 도구를 선택한다.
6. LLM이 도구 근거를 이용해 답변을 구성한다. 서버가 최종 응답을 검증한 뒤 앱에 표시한다.
7. 사용자가 변경 제안을 적용하면 서버가 비교 당시 상태 버전을 확인하고 상태를 갱신한다. 오래된 비교는 현재 조건으로 재계산한다.

초기 제안 상한은 사용자 한 턴당 도구 호출 5회다. 일시적 조회 오류는 1회만 재시도하고 전체 한도에 포함한다. 반복 실패·시간 초과·호출 한도 도달 시 현재 조건을 보존하고 복구 안내로 종료한다. 실제 상한은 지연시간과 과업 완료율을 측정해 조정한다.

## 도구 계약

아래 이름은 구현할 래퍼의 제안이다. 아직 실행 가능한 도구 API라는 뜻은 아니다.

| 도구 | 입력 | 결과 | 기존 구현 |
| --- | --- | --- | --- |
| `search_products` | 검증된 조건·상태 버전 | 후보 최대 3개·계산 비용·추천 근거 | `recommend`, `rankProducts` |
| `compare_budget` | 현재 조건·기준 추천 ID | 예산별 후보 및 상위 추천 변화 | `budgetAlternatives` |
| `explain_recommendation` | 추천 실행 ID·상품 ID | 점수 항목·조건 통과 근거 | 엔진 결과를 근거 계약으로 포장 |
| `inspect_constraints` | 조건·카탈로그 스냅샷 | 미확인 항목·제약별 후보 현황 | 신규 검증 래퍼 |
| `lookup_product_evidence` | 상품 ID·질문 속성 | 확인된 속성·출처 또는 미확인 | 카탈로그 조회 래퍼 |

기존 함수는 [추천 엔진](../../lib/engine.mjs), [예산 비교 엔진](../../lib/counterfactual.mjs)에 있다. 공통 반환값에는 상태, 상태 버전, 실행·근거 ID를 포함하도록 설계한다. 상품 설명·검색 문서의 지시문은 데이터로만 취급한다.

정형 상품·금액은 구조화 조회를 사용한다. 정책 문서 RAG와 도구 재사용을 위한 MCP는 후속 확장이며 초기 에이전트의 필수 조건이 아니다.

## 조건·메모리·사용자 확인

- 언급하지 않은 조건은 유지한다. 명시적 해제와 변경 없음, 불명확한 값을 구분한다.
- 예산·수량·제외 조건은 요약 문장에만 의존하지 않고 구조화 상태로 보존한다.
- 단기 메모리는 세션 조건·대화·미해결 질문·추천·도구 결과로 구성한다. 장기 선호는 사용자가 명시적으로 저장한 범위만 활용한다.
- 상품 검색·계산·가상 비교는 자동 수행한다. 모든 도구 호출에 승인을 요구하지 않는다.
- 사용자의 명확한 조건 수정 요청은 검증 후 반영하고 변경 내역·되돌리기를 제공한다. 모호한 조건은 확인 질문을 한다.
- 에이전트가 제안한 예산 증액·제외 조건 완화는 사용자 적용 전까지 실제 상태를 변경하지 않는다.
- 비교는 상태 복제본에서 수행하고 ‘후보 추가’와 ‘상위 추천 변경’을 구분한다.
- 가격·배송·재고·성분의 근거가 부족하면 확정하지 않는다. 현재 상품 데이터의 배송·재고 등 데모 속성을 실제 거래 정보로 설명하지 않는다.
- 내부 추론 원문 대신 실행 상태·변경 내용·검증된 근거를 표시한다. 주문·결제는 초기 범위 밖이다.

## 동작 예시

다음은 동작을 설명하는 예시이며 실제 검색 결과가 아니다.

| 사용자 요청 | 에이전트 행동 | 서버·사용자 제어 |
| --- | --- | --- |
| “부모님 선물, 예산 10만 원” | 예산 기준·수량 등 필요한 정보 질문 | 모호한 조건을 확정하지 않음 |
| “두 세트 총액이고 배송비 포함, 같은 차 세트로” | `search_products` 선택 | 엔진이 필터·정렬·금액 계산 |
| “왜 이걸 추천했어?” | `explain_recommendation` 선택 | 도구 근거에 있는 사실로 설명 |
| “2만 원 더 쓰면?” | `compare_budget` 선택 | 실제 10만 원 유지, 가상 12만 원 비교 |
| “12만 원 적용” 버튼 | 서버의 확정된 적용 경로 | 상태 버전 확인 후 갱신·재계산 |

## 후속 목표: Rule-based Hybrid와 비교

두 구조는 같은 인증·상품 DB·조건 검증·추천 엔진·예산 비교 기능을 공유한다. **차이는 LLM 호출 유무보다 실행 흐름을 누가 제어하는가에 있다.**

| 구분 | LLM Agent | Rule-based Hybrid |
| --- | --- | --- |
| 다음 행동·도구 선택 | LLM | 백엔드 Router |
| 명확한 조건 처리 | LLM 해석·검증된 도구 경로 | 규칙 파서·상태 관리 |
| 모호한 자연어 | LLM 판단 후 질문·도구 실행 | 필요할 때 제한적 단일 LLM 호출 또는 질문 |
| 추천·금액·예산 비교 | 공통 PASS 엔진 | 동일 PASS 엔진 |
| 재계획 | 제한된 에이전트 루프 | 명시적인 서버 정책; LLM 도구 선택 루프 없음 |
| 최종 응답 | 근거 기반 LLM 생성·서버 검증 | 템플릿 우선, 필요시 제한적 LLM |

‘추천할 때만 LLM을 실행한다’를 두 구조의 구분 기준으로 삼지 않는다. Hybrid는 명확한 추천 요청을 LLM 없이 처리할 수 있고, 추천 외 요청도 복잡한 해석이 필요하면 LLM을 사용할 수 있다. 호출 수·비용·정확도 개선은 구현 후 측정할 가설이다.

후속 실험은 다음 2 × 2 조건을 목표로 한다. 각 조건은 동일한 초기 상태의 독립된 세션에서 시작하고, 같은 상품 스냅샷·추천 규칙·반사실 계산·도구 접근 권한을 사용한다. 종단 간 실행 제어 실험에서는 실제 선택된 도구와 상태에 따른 결과 차이도 측정한다. 설명 제시 효과를 분리하는 실험에서는 후보·순위·과업을 고정한다.

| 조건 | 실행 구조 | 대조·반사실 설명 |
| --- | --- | --- |
| A | LLM Agent | 없음 |
| B | LLM Agent | 있음 |
| C | Rule-based Hybrid | 없음 |
| D | Rule-based Hybrid | 있음 |

비교 지표는 LLM·도구 호출 수, 토큰 비용, 응답 시간, 조건 정확도, 제약 위반, 과업 완료율, 설명 이해도·유용성·신뢰도다. 실험 조건 배정·로그 수집·Hybrid 구현은 이번 문서화 범위에 포함하지 않는다.

## 구현 순서와 완료 기준

1. 기존 엔진을 공통 도구 계약으로 감싸고 기존 추천·금액·반사실 계산을 유지한다.
2. 조건 상태·버전·미해결 질문·가상 비교 격리와 서버 검증을 구현한다.
3. 도구 선택 → 실행 → 관찰 → 재계획/종료의 단일 에이전트 루프를 구현한다.
4. 추천·질문·변경 제안·되돌리기·오류 복구 UI를 연결한다.
5. 프롬프트 예시와 분리한 평가 시나리오에서 동작과 호출 제한을 검증한다.
6. LLM Agent를 기준으로 후속 Hybrid 및 2 × 2 비교 실험을 구현한다.

최소 완료 기준은 모호한 요청에 질문하고, 검증된 조건으로 도구를 선택해 추천하며, 가상 예산을 실제 조건과 분리하고, 호출 한도 안에서 종료하는 것이다. 예산·제외 조건 위반, 제안의 무승인 적용, 도구 결과에 없는 상품·금액 생성은 평가에서 실패로 기록한다. 이 문서는 해당 기준을 달성했다는 검증 보고서가 아니다.
