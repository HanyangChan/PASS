# PASS 평가 UI 구현 명세

문서 버전: 1.0  
대상 경로: `/study`  
연구 버전: `pass-explanation-pilot-v3-pre-post`

## 1. 목적과 범위

이 UI는 명절 선물 추천에서 예산 변화에 대한 비교 설명이 다음 세 항목에 미치는 영향을 평가한다.

1. 추천 결과 이해도
2. 선택 확신
3. 주관적 판단 부담

평가 화면은 일반 추천 대화와 분리한다. 실제 결제, 회원가입, 개인정보 입력, 서버 자동 전송은 포함하지 않는다. 모든 상품은 실험용 데이터이며 Gemini 호출 없이 고정 카탈로그와 추천 엔진으로 동작해야 한다.

## 2. 전체 사용자 흐름

```text
안내·참여 확인
  → 사전 설문
  → 과제 1 상품 선택
  → 과제 1 사후 설문
  → 중간 휴식
  → 과제 2 상품 선택
  → 과제 2 사후 설문
  → 최종 비교 설문
  → 완료·JSON 저장
```

모든 단계에서 `평가 중단`을 제공한다. 중단하면 현재까지의 응답을 보존한 종료 화면으로 이동한다. 브라우저 새로고침이나 이탈 시 데이터가 사라질 수 있음을 시작 화면에서 안내한다.

## 3. 공통 레이아웃

- 상단: 브랜드 `마음`, 화면명 `추천 설명 평가`.
- 단계 표시: `1. 사전 설문`, `2. 두 과제 · 사후 설문`, `3. 최종 비교`.
- 현재 단계만 강조하며 `aria-current="step"`을 제공한다.
- 본문 최대 너비 1,160px, 설문 패널 최대 너비 780px.
- 본문 글자 16px 이상, 주요 버튼과 선택지는 높이 44px 이상.
- 화면 전환 시 페이지 상단으로 이동하고 새 화면의 `h1`에 초점을 준다.
- 주요 행동은 파란색 채움 버튼, 중단은 테두리 버튼으로 표현한다.
- 모바일에서는 상품 카드와 선택지를 한 열로 배치한다. 가로 스크롤이 생기면 안 된다.

## 4. 화면별 명세

### S0. 안내 및 참여 확인

필수 요소:

- 평가 구성과 예상 행동 설명
- 실험용 상품이며 구매가 발생하지 않는다는 안내
- 수집 항목, 로컬 기록, JSON 전달 방식 안내
- 자유 응답에 개인정보를 쓰지 말라는 안내
- 참여 확인 스위치
- `사전 설문 시작` 버튼

동작:

- 참여 확인 전에는 시작 버튼을 비활성화한다.
- 시작 시 무작위 세션 ID와 0~3 배정 그룹을 생성한다.
- 이름, 전화번호, 이메일은 입력받지 않는다.

### S1. 사전 설문

모든 문항은 단일 선택이며 기본 선택값을 두지 않는다.

| 키 | 문항 | 선택지 |
| --- | --- | --- |
| `age` | 연령대 | 18–29 / 30–39 / 40–49 / 50–59 / 60세 이상 / 응답하지 않음 |
| `shopping` | 최근 6개월 온라인 구매 빈도 | 없음 / 월 1회 미만 / 월 1–3회 / 주 1회 이상 |
| `gifts` | 최근 1년 명절 선물 선택 횟수 | 없음 / 1회 / 2회 이상 |
| `chatbot` | 챗봇 상품 추천 사용 횟수 | 없음 / 1–2회 / 3회 이상 |
| `familiarity` | 온라인 상품 비교 친숙도 | 전혀 익숙하지 않음~매우 익숙함 5단계 |

동작:

- `n / 5개 응답 완료`를 즉시 갱신한다.
- 5개 모두 응답해야 `사전 설문 완료 · 첫 과제 시작`을 활성화한다.
- 사전 설문 완료 시간은 `preSurvey.durationMs`로 기록한다.

### S2. 상품 선택 과제

상단에는 `과제 n / 2`, 과제 제목, 받는 사람과 선호·제외 조건을 표시한다.

두 과제 정의:

| 과제 | 조건 | 처음 예산 | 비교 예산 |
| --- | --- | ---: | ---: |
| 부모님 선물 | 덜 단 상품, 견과류 제외, 배송비 포함 | 30,000원 | 42,000원 |
| 친구 선물 | 덜 단 상품, 커피 제외, 배송비 포함 | 60,000원 | 72,000원 |

필수 컴포넌트:

- 처음 예산/비교 예산 단일 선택 컨트롤
- 현재 적용 예산 표시
- 추천 상품 카드 목록
- `선택하지 못했어요` 선택지
- 과제 완료 상태와 `선택 확정 · 사후 설문` 버튼

상품 카드 표시 항목:

- 추천 순위
- 상품명
- 배송비 포함 가격
- 현재 조건과 연결한 추천 이유
- 선택 버튼

동작 규칙:

- 진입 시 처음 예산이 적용된다.
- 두 예산을 모두 한 번 이상 확인해야 한다.
- 상품 하나 또는 `선택하지 못했어요`를 골라야 한다.
- 예산을 낮춰 선택 상품이 후보에서 사라지면 선택을 해제한다.
- 위 두 완료 조건을 만족해야 사후 설문 버튼을 활성화한다.
- 사후 설문으로 이동하면 상품 선택은 확정되어 수정할 수 없다.

### S2-B. 비교 설명 카드

조건 B에서만 상품 목록 아래에 표시한다. 조건 A에서는 영역 자체를 렌더링하지 않는다.

표시 항목:

- 처음 예산 → 비교 예산
- 다른 조건은 유지된다는 문구
- 최상위 추천 변경 여부
- 후보 수 변화
- 새로 포함된 대표 상품과 순위
- 처음 예산에서 제외된 이유
- 더 비싼 상품을 자동으로 우선하지 않는다는 순위 설명

A/B 실험 통제 조건:

- A와 B의 상품, 가격, 순위, 예산 버튼, 선택 동작은 같아야 한다.
- B에서만 비교 설명을 추가한다.
- B에만 애니메이션, 다른 색의 상품 카드, 더 빠른 응답 등 별도 이점을 주면 안 된다.

### S3. 과제별 사후 설문

필수 객관식 4개:

| 키 | 측정 개념 | 문항/응답 |
| --- | --- | --- |
| `topChanged` | 이해도 | 첫 추천이 바뀜 / 유지됨 / 모르겠음 |
| `candidateCount` | 이해도 | 후보 증가 / 동일 / 감소 / 모르겠음 |
| `confidence` | 선택 확신 | 전혀 확신하지 못함~매우 확신함 5단계 |
| `effort` | 판단 부담 | 전혀 어렵지 않았음~매우 어려웠음 5단계 |

`selectedId === "none"`이면 확신 문항을 `선택하지 않기로 한 판단이 적절하다고 얼마나 확신하나요?`로 바꾼다.

선택 자유 응답 3개:

- 예산 변경이 추천 결과에 준 영향
- 선택에 가장 영향을 준 정보
- 이해하기 어렵거나 부족했던 정보

동작:

- 자유 응답은 각각 최대 1,000자이며 글자 수를 표시한다.
- 자유 응답 입력 과정은 이벤트 로그에 남기지 않고 최종 텍스트만 저장한다.
- `필수 n / 4개 응답 완료`를 표시한다.
- 필수 4개 완료 후에만 제출할 수 있다.
- 이해도 정답은 제출 후 내부 계산하며 사용자에게 보여주지 않는다.

### S4. 과제 사이 휴식

- `첫 과제를 마쳤습니다` 제목과 휴식 안내를 표시한다.
- `두 번째 과제 시작`을 누른 시점부터 두 번째 과제 시간을 측정한다.
- 휴식 시간은 두 번째 과제 수행 시간에 포함하지 않는다.
- `여기서 마치기`를 제공한다.

### S5. 최종 비교 설문

필수 요소:

- 첫 번째와 두 번째 과제명을 순서대로 표시
- `첫 번째 화면 / 두 번째 화면 / 차이 없음 / 판단하기 어려움` 단일 선택
- 선택 이유 자유 응답, 최대 1,000자, 선택 사항
- `최종 설문 완료` 버튼

첫 번째 또는 두 번째 화면을 고른 경우 실제 배정 순서를 기준으로 A/B 조건으로 변환해 `preferredCondition`에 저장한다. 차이 없음과 판단 어려움은 `null`로 저장한다.

### S6. 완료 또는 중단

- 완료/중단 상태를 명확히 표시한다.
- 완료한 과제 수와 기록 수를 표시한다.
- `평가 기록 저장 (JSON)` 버튼을 제공한다.
- 저장 성공 요청 후 상태 메시지를 표시한다.
- 일반 선물 대화로 돌아가는 링크를 제공한다.
- 파일명은 `PASS-{sessionId}.json` 형식이다.

## 5. 상태 전이

| 현재 상태 | 이벤트 | 조건 | 다음 상태 |
| --- | --- | --- | --- |
| `intro` | 시작 | 참여 확인 완료 | `pre` |
| `pre` | 사전 설문 제출 | 필수 5개 완료 | `running` |
| `running` | 선택 확정 | 두 예산 확인 + 선택/미선택 | `post` |
| `post` | 사후 설문 제출 | 필수 4개 완료 | `between` 또는 `final` |
| `between` | 두 번째 과제 시작 | 항상 | `running` |
| `final` | 최종 설문 제출 | 비교 선택 완료 | `complete` |
| 모든 미완료 상태 | 중단 | 항상 | `stopped` |

완료 또는 중단 상태에서는 추가 입력 이벤트를 무시한다. 이미 제출한 과제는 중복 제출할 수 없다.

## 6. A/B 배정 규칙

참가자마다 다음 네 조합 중 하나를 무작위 배정한다.

1. 부모님 A → 친구 B
2. 부모님 B → 친구 A
3. 친구 A → 부모님 B
4. 친구 B → 부모님 A

각 참가자는 A와 B를 한 번씩 사용한다. 실제 모집 인원이 네 그룹에 균등하게 들어가는지는 연구자가 모집 현황에서 별도로 확인한다.

## 7. 데이터 저장 명세

최상위 객체:

| 필드 | 내용 |
| --- | --- |
| `version` | 연구 버전 |
| `id` | 무작위 세션 ID |
| `group`, `sequence` | 배정 그룹과 과제/조건 순서 |
| `status` | `pre`, `running`, `post`, `between`, `final`, `complete`, `stopped` |
| `preSurvey` | 사전 설문 응답과 소요 시간 |
| `trials` | 완료한 과제별 선택, 사후 응답, 이해도 정답 여부, 시간 |
| `finalSurvey` | 최종 비교, 이유, 선호 조건 |
| `events` | 시작, 선택, 예산 변경, 제출, 중단 이벤트 |
| `taskDefinitions` | 내보낸 시점의 과제 정의 |
| `surveyDefinitions` | 내보낸 시점의 문항과 응답 코드 |

시간은 밀리초로 저장한다.

- `taskDurationMs`: 과제 시작부터 선택 확정까지
- `selectionMs`: 마지막 상품 선택 시점
- `surveyDurationMs`: 사후 설문 소요 시간
- `durationMs`: 과제 시작부터 사후 설문 제출까지

자동 서버 전송은 하지 않는다. 내보내기에는 채팅 원문, 이름, 연락처, 계정 ID를 포함하지 않는다.

## 8. 접근성 요구사항

- 단일 선택 그룹은 네이티브 라디오 버튼 또는 `role="radiogroup"` + `role="radio"`로 구현한다. 버튼을 사용할 경우 `aria-pressed`만으로 체크박스처럼 읽히지 않게 검증한다.
- 모든 선택 그룹에는 화면에 보이는 질문을 접근 가능한 이름으로 연결한다.
- 키보드만으로 모든 선택, 제출, 중단, JSON 저장이 가능해야 한다.
- 선택 상태를 색만으로 표현하지 않고 텍스트·테두리·접근성 상태를 함께 사용한다.
- 비활성 버튼은 비활성 이유를 바로 앞의 진행 상태 문구로 설명한다.
- 진행 상태와 저장 완료 메시지에는 `role="status"`를 사용한다.
- 초점 표시를 제거하지 않는다. 최소 3px 외곽선을 권장한다.
- 200% 확대와 360px 폭에서 내용 누락이나 가로 스크롤이 없어야 한다.

## 9. 오류 및 예외 처리

- 유효하지 않은 문항 키, 선택값, 상품 ID, 예산값은 상태에 반영하지 않는다.
- 후보에 없는 상품 ID는 선택할 수 없다.
- 1,000자를 넘는 자유 응답은 저장하지 않는다.
- 제출 중복 클릭은 한 번만 처리한다.
- JSON 생성 또는 다운로드가 실패하면 저장되지 않았다는 오류와 재시도 버튼을 표시해야 한다.
- 평가 흐름은 Gemini 상태와 무관하게 동작해야 한다.

## 10. 구현 완료 기준

- 안내부터 JSON 저장까지 전체 흐름을 중단 없이 완료할 수 있다.
- 필수 응답 전에는 다음 단계 버튼이 비활성화된다.
- 두 예산을 모두 보지 않으면 상품 선택을 확정할 수 없다.
- A/B에서 비교 설명 외의 추천 결과와 조작 방식이 동일하다.
- 미선택 참가자에게 맞는 확신 문항이 표시된다.
- 이해도 정답 2개가 추천 엔진 결과와 비교되어 저장된다.
- 과제 시간, 설문 시간, 휴식 시간이 구분된다.
- 완료와 중단 모두 JSON으로 내보낼 수 있다.
- 데스크톱, 모바일, 키보드, 스크린리더 기본 흐름을 확인한다.
- 자동 테스트와 프로덕션 빌드가 통과한다.

구현 문항의 단일 소스는 `lib/study-surveys.mjs`, 연구 절차의 단일 소스는 `evaluation/study-protocol.md`로 유지한다. 화면 문구를 바꿀 때 이 두 파일과 내보내기 정의가 서로 달라지지 않도록 한다.
