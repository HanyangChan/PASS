# A 현재 설정 vs B 풀 에이전트 비교

저장소 루트에서 `npm run benchmark:agents`로 실행한다. 실제 서버 LLM 키·모델 설정을 사용하며 과금이 발생한다. 로컬/운영 에이전트 설정은 바꾸지 않는다. 결과는 `docs/verification/agent-comparison-2026-11-06.json`에 저장한다.

동일한 20개 과제를 3회씩 A `a-router`와 B `full-chat`에 실행한다. 기본 A 모드는 현재 `A_ROUTER_LLM_MODE` 값이다. 양쪽은 같은 초기 세션·사용자 문장·공통 엔진·고정 상품 카탈로그 3,376개를 쓴다. 카탈로그 날짜는 2026-11-06으로 고정하고 원본 해시를 기록한다. 인증과 세션은 합성 대체물이므로 실제 계정·사용자 데이터에 쓰지 않는다.

과제 구성: 정형 업무 9개, 안전·확인 5개, 대화 2개, 자연어 업무 3개, 3턴 연속 대화 1개. 따라서 1개 에이전트당 과제 실행 60개, API 요청 66개다. 반복마다 과제 순서를 순환하고 A/B 실행 순서를 번갈아 배치한다. 공급자 요청은 순차 실행한다. 별도 워밍업은 하지 않으며 서버/공급자의 캐시 효과를 제거하지 않는다.

정확도는 미리 정의한 조건의 반영·보존, 적절한 확인 질문, 정상 추천·금액·가상 비교·설명 근거를 모두 충족한 **과제 성공률**이다. 날짜 생신/생일 및 집합 필드의 순서는 동등 처리한다. 추천 결과의 정답은 같은 엔진에 기대 조건을 넣어 계산한다. 따라서 이 평가는 자연어 해석·실행 제어·상태 관리의 정확도이며 상품 품질·랭킹 자체의 타당성이나 사용자 만족도 평가는 아니다. 인사와 감사는 업무 점수와 별도 그룹으로도 제공한다.

지연시간은 실제 API 핸들러 진입부터 응답 JSON 수신까지 측정한다. 실제 공급자 네트워크와 엔진 계산은 포함하고, 브라우저/UI·실제 Supabase 인증·DB 조회 네트워크는 제외한다. 모든 실패를 성공률과 전체 지연 집계에 포함한다. 평균/중앙값/p95를 요청별 및 과제별로 구분한다. 3턴 과제의 시간은 해당 3개 요청 합계다.

실제 설정 그대로 비교하므로 A/B가 전송한 `reasoning` 옵션도 기록한다. 같은 모델을 사용해도 요청 옵션·출력 형식·토큰 상한·호출 횟수는 구현별로 다르다. 결과를 오직 에이전트 구조만의 인과 효과라고 해석하지 않는다. 반복 3회는 작은 표본이며 문구는 고정되어 있다. 테스트 중 에이전트 코드를 수정하지 않고 실패도 그대로 보고한다.

## B 피드백 예산 비교

`npm run benchmark:feedback`은 B/피드백 최대 1회/최대 2회 모드를 같은 실행에서 비교한다. 기존 20개 과제는 회귀 확인용 1회씩, 새 문구 10개는 각 3회씩 실행한다. 전부 같은 모델과 reasoning=false를 사용한다. 검토 횟수 상한은 행동당 값이며, 2회 모드도 첫 검토가 통과하면 추가 검토를 하지 않는다. 피드백 모드의 전체 논리 호출 상한은 10회이고 기존 B는 6회다. 검토·수정을 포함한 실제 호출 수와 사용량도 측정한다.

결과는 `docs/verification/feedback-tradeoff-2026-11-06-{regression,holdout}.json`과 요약 JSON에 저장한다. [실측 보고서](../../docs/verification/feedback-tradeoff-2026-11-06.md)를 참고한다. 같은 총 계산량에서 검토만의 효과를 분리한 실험은 아니며, 프롬프트 개선에 사용한 기존 과제와 새 문구 점수를 섞어 일반화 성능이라고 부르지 않는다.
